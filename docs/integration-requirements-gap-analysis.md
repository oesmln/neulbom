# 통합 요구사항 대비 현재 구현 갭 분석

> 기준 브랜치: `develop` (`af96083`)
>
> 작업 이슈: [#71](https://github.com/oesmln/neulbom/issues/71)
>
> 상위 통합 이슈: [#70](https://github.com/oesmln/neulbom/issues/70)

이 문서는 통합 요구사항과 현재 코드의 차이를 기능별로 고정하기 위한 기준 문서다. 아래 상태는 현재 `develop`을 정적 점검한 결과이며, 구현 완료로 표시된 항목도 실제 사용자 흐름과 통합 테스트가 끝나기 전까지 최종 완료로 보지 않는다.

## 상태 정의

- **구현됨**: 관련 코드와 API가 존재하며 요구사항의 핵심 동작을 수행한다.
- **부분 구현**: 일부 흐름만 구현됐거나 요구사항의 추가 조건이 빠져 있다.
- **미구현**: 요구사항을 충족하는 코드/API가 없다.
- **결정 필요**: 정책·문구·외부 연동 범위를 먼저 확정해야 한다.

## 우선순위와 후속 이슈 제안

상위 이슈 #70 아래에 다음 순서로 분리한다.

1. **인증·역할 상태 통합**: 이메일 인증, OAuth 신규/기존 계정, 로그아웃 후 재진입 플래그
2. **가입 필수 동의와 철회**: 약관·개인정보·민감정보·공유 범위·설정 철회
3. **초대코드·프로필 정책**: 고령자 사후 입력, 보호자 코드 관리, 선택 프로필
4. **초기 AI 온보딩·baseline**: AI 대화 화면 재사용, 단계 저장, CIST 기준값·1회 보상
5. **XP 정책 고정**: 레벨/보상/상한/멱등성
6. **일기·리포트 자동화**: 자정 집계, 누락 보정, 제외 규칙, 공유 응답
7. **보호자 기록·알림·설정 UI**: 기록 탭 통합, 상단 알림, 설정 구조
8. **전문의 예약**: 예약 도메인·API·화면 (외부 연동 범위 결정 후 착수)
9. **역할별 E2E·통합 검증**: 가입→동의→온보딩→로그아웃→재로그인→보호자 조회 시나리오

## 프론트엔드 디자인 원칙

- 기존 `frontend/src/theme` 토큰과 `frontend/src/components/ui.tsx` 공통 컴포넌트를 우선 재사용한다.
- 초기 온보딩은 새 디자인 시스템을 만들지 않고 `ElderAiChat`의 말풍선·입력·큰 버튼 형태를 단계형으로 확장한다.
- 고령자 화면은 큰 글씨, 단순한 선택지, 한 화면 한 과제를 유지한다.
- 보호자 기록 화면은 기존 캘린더 시각 언어를 유지하되, 일기와 리포트를 카드와 필터로 구분한다.
- 네비게이션 명칭과 아이콘 변경은 화면 이동 경로 및 접근성 라벨 테스트와 함께 반영한다.

## 완료 전 공통 검증 시나리오

- [ ] 이메일 미인증 계정이 정상 서비스로 진입하지 못하고 재전송할 수 있다.
- [ ] 신규 소셜 계정만 역할 선택을 보며, 기존 계정은 저장된 역할로 진입한다.
- [ ] 로그아웃 후 재로그인 시 역할 선택 화면이 다시 나오지 않는다.
- [ ] 고령자는 필수 동의 후 온보딩을 중단·재개할 수 있고, 온보딩/CIST가 일반 일기와 리포트에 섞이지 않는다.
- [ ] CIST baseline과 최초 보상이 재시도해도 중복 생성되지 않는다.
- [ ] 보호자 초대코드 없이 가입한 고령자가 설정에서 나중에 연결할 수 있다.
- [ ] 동의 철회 후 음성·분석·보호자 조회가 공유 범위에 맞게 차단된다.
- [ ] 자정 작업 실패 후 다음 실행에서 누락 날짜가 보정된다.
- [ ] 보호자 화면이 `홈·기록·추이·예약·설정`으로 표시되고 알림은 상단에서 열린다.
- [ ] 백엔드 `./gradlew test`, `./gradlew build`와 프론트 타입 검사/테스트가 통과한다.
